# Deep Agent 666 产品方向与 Deep Agents 边界设计

> 日期：2026-06-27
> 状态：proposed

## 1. 背景

当前项目已经完成 V1-V27 的本地优先通用 Agent 基线，包含：

- 基于 `create_deep_agent(...)` 的单 agent preset 体系
- 基于 LangGraph `create_agent + @tool + Command` 的 coordinator 工作台
- CopilotKit 驱动的聊天、timeline、线程恢复、A2UI diff preview

但产品下一阶段不能只按“功能点堆叠”推进，必须先明确一件事：

`deepagents` 是执行内核，不是完整产品框架。

后续产品方向必须同时满足两类约束：

- 满足用户对通用型 Agent 的产品预期：多模态输入、过程透明、人工接管、结构化输出、可编排能力
- 尊重当前后端内核的真实能力边界：哪些可直接利用，哪些必须由我们自行封装

## 2. 北极星定位

本产品的第一性定位定义为：

`一个面向真实材料和真实操作的、可观察、可打断、可编排的执行型工作台。`

这一定义刻意避免把产品描述成“万能聊天助手”，原因如下：

- 用户的真实输入是仓库、文档、PDF、图片、网页、命令和数据，而不是单一文本框
- 用户需要看到 Agent 在做什么，而不是只看到最终答案
- 用户需要在执行中接管、修正和回退，而不是一次性托管给黑盒
- 用户需要可继续流转的结构化结果，而不是一坨长文本

## 3. 用户原则

后续产品需求均必须满足以下五条原则：

1. 输入别反人类：支持围绕真实材料工作的输入方式，而非要求用户手动转写
2. 过程别搞黑盒：工具调用、资料读取、代码修改、子 agent 委托都必须可见
3. 允许随时踩刹车：执行过程必须支持中止、重试、修改步骤和恢复
4. 输出别吐一坨字：结果必须支持 Markdown、代码高亮、表格、折叠和导出
5. 别教用户做事：高阶用户应能通过工作流预设和插件组合能力，而不是被困在单一聊天框

## 4. 真实后端边界

### 4.1 当前后端的准确描述

当前后端不是“纯 deepagents 产品”，而是如下组合：

- `deepagents`：单 agent 执行内核、工具调用、内建文件系统/执行抽象、HITL/interrupt、subagent 能力
- `LangGraph/LangChain`：coordinator 自定义编排与共享状态更新
- `CopilotKit`：运行时桥接、线程恢复、前端事件承载、A2UI surface
- `Next.js workbench`：用户可见的 timeline、artifact、threads、diagnostics

因此，“产品后端是 deepagents 吗”的准确回答应为：

`deepagents 是核心执行内核，但产品能力并不由 deepagents 独立构成。`

### 4.2 Deep Agents 可直接利用的能力

以下能力可被视为当前路线的稳定基础：

- Tool calling 与文件/命令执行骨架
- 同步子 agent 与异步子 agent 机制
- `interrupt_on` 驱动的人工审批中断
- `state_schema` 与 middleware 扩展点
- checkpointer / store / backend 抽象

这些能力适合作为执行层，不适合作为完整产品层。

### 4.3 Deep Agents 不能直接替我们完成的部分

以下能力不应误判为框架原生能力：

- 用户侧多模态输入产品体验
- 统一的过程时间线与可视化状态机
- “随时停止 / 修改计划 / Undo” 级别的人机协作控制台
- artifact 工作台、导出系统、富文本结果系统
- 终端用户可操作的工作流编排台和插件管理台

这部分必须由本项目自行设计和封装。

## 5. 能力分层

后续系统按四层划分：

### 5.1 Execution Kernel

职责：

- 执行模型调用
- 调度工具
- 调度子 agent
- 承载最小图状态
- 处理审批/中断/恢复原语

主要技术：

- `deepagents`
- `LangGraph`
- `LangChain`

### 5.2 Runtime Orchestration

职责：

- 把 kernel 事件转为稳定的产品运行时协议
- 管理线程、恢复、重放、取消、降级状态
- 统一 tool/subagent/artifact/approval/cancel 事件语义

主要技术：

- CopilotKit runtime
- 自定义 AG-UI / A2UI 事件封装
- SQLite thread runner + 本地缓存

### 5.3 Material Ingestion

职责：

- 统一处理 repo、txt/md、pdf/docx、图片、网页、日志等材料输入
- 决定解析方式、截断策略、缓存策略与附件生命周期
- 为 agent 提供稳定材料引用，而不是裸文本拼接

主要技术：

- 现有 document tools
- 后续新增 image / web / dataset ingestion adapters

### 5.4 User Workbench

职责：

- 展示过程、结果、工件和错误
- 支持中止、重试、回放、审批、编辑计划
- 提供 preset、workflow、plugin、artifact 导出入口

主要技术：

- Next.js
- CopilotKit React
- A2UI renderers

## 6. 产品策略

### 6.1 主战场不是单一聊天，而是双场景共享内核

下一阶段不建议在“知识工作台”和“工程工作台”之间二选一，而应共享同一执行内核，同时发展两条高频主链：

- 工程工作台：仓库、文件、命令、diff、验证、恢复
- 知识工作台：PDF、DOCX、网页、图片、摘录、结构化整理

原因：

- 两条场景都依赖同一套材料输入、可观测过程、人工干预和结构化输出能力
- 先共享内核再分场景，比先做两个割裂产品更稳
- 当前项目已有工程工作台基线，补知识工作台更容易形成复用闭环

### 6.2 当前阶段不承诺的事项

为避免产品定义失真，以下内容不应在当前阶段对外承诺：

- 任意图片均具备高质量专业视觉推理
- 任意外部副作用操作都支持真实 Undo
- 面向所有行业的一步到位通用工作流平台
- 低代码可视化编排平台优先于核心执行工作台

## 7. 分期路线

### 7.1 Phase A：统一运行时协议

目标：

- 统一 tool、subagent、artifact、approval、cancel、resume 事件模型
- 把现有 V1/V2 不同状态流收口为单一可消费协议
- 为后续多模态输入和工作流编排建立稳定底座

验收标准：

- 所有 agent 运行都能在同一 timeline 中展示稳定事件
- 前端不再依赖每个工具的临时字符串解析来判断状态
- 中止、失败、恢复、重试事件拥有明确语义

### 7.2 Phase B：材料输入层产品化

目标：

- 统一支持 repo、txt/md、pdf/docx、基础 image、网页链接
- 构建 ingestion pipeline：接收、解析、截断、缓存、引用
- 让 Agent 消费“材料对象”，而不是只消费用户手动拼接文本

验收标准：

- 用户可直接上传/选择 PDF、DOCX、图片、仓库目录作为任务输入
- 材料被解析后可在 UI 中看到来源、摘要和状态
- Agent 在运行中可引用这些材料，而不是要求用户自行复制内容

### 7.3 Phase C：过程透明与人工接管

目标：

- 完成可视化 timeline、工具状态、子 agent 委托状态
- 支持 stop、retry、resume、approval、edit-plan
- 把“可中断”从技术能力升级为用户可操作能力

验收标准：

- 运行中的每个关键动作都具备可见状态
- 用户可在执行中停止任务，而不是只能等待结束
- 审批/恢复动作能在同线程同工作台内完成

### 7.4 Phase D：结构化结果工作台

目标：

- 扩展 A2UI / artifact rendering，不只覆盖文件 diff
- 提供 Markdown、代码、表格、摘要卡片、导出入口
- 让结果具备二次消费能力

验收标准：

- 非纯文本结果可落为独立 artifact，而不是只显示在聊天流里
- 长结果支持折叠和重点字段高亮
- 用户可一键导出核心结果

### 7.5 Phase E：工作流与插件基础设施

目标：

- 提供可复用任务模板、工具预设、插件开关
- 允许高阶用户把常用模式固化为工作流积木
- 形成“聊天 + 工作台 + workflow” 三位一体产品

验收标准：

- 至少支持若干官方内建 workflow preset
- 插件能力具备基础启停与权限可见性
- 用户无需重写 prompt 即可复用高频任务路径

## 8. 优先级判断

推荐优先级如下：

1. Phase A 统一运行时协议
2. Phase C 过程透明与人工接管
3. Phase B 材料输入层产品化
4. Phase D 结构化结果工作台
5. Phase E 工作流与插件基础设施

理由：

- 如果事件协议不统一，后续所有 UI 与控制能力都会继续碎片化
- 如果不可打断、不可恢复，Agent 再“聪明”也不适合作为生产工具
- 多模态输入重要，但前提是输入进来之后能被看见、能被控制、能产出结构化结果

## 9. 对现有代码的含义

本设计对当前项目的直接含义如下：

- 继续保留 `deepagents` 作为 V1 单 agent 的执行内核
- 继续允许 coordinator 采用 LangGraph 自定义编排，而不是强行回退为纯声明式子 agent
- 后续新增能力优先围绕“统一 runtime 事件协议”设计，而不是继续堆零散 UI 组件
- 多模态第一阶段以文档和基础图片支持为主，不对深度视觉理解做过度承诺
- A2UI 下一步重点应从单一 `DiffPreview` 扩展到通用 artifact surface 体系

## 10. 成功定义

以下状态可视为本路线取得阶段性成功：

- 用户可以直接提交真实材料，而不是先手工转写
- 用户能实时看到 Agent 在做什么、为什么卡住、能如何接管
- 用户能在同一线程内完成中止、审批、重试、恢复
- 输出结果可被展示、导出、复用，而不是只作为一段聊天文本存在
- 工程和知识两类工作台共享同一内核与运行时协议，而不是各自为政
